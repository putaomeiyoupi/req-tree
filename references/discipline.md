# 写入纪律、每周巡检与脱敏

## 一、这套系统的唯一失败模式

**不是设计出错，而是没人记。**
任何「回头一起整理」的念头都会导致追溯链断裂：三天后你只知道「加了这几个需求」，
却再也说不出「1.3.1 是怎么冒出来的」。因此纪律必须内建到工作流里，不靠自觉。

---

## 二、触发即落库（最高优先级）

### 收工/开工两个动作（决定「跨次能不能接上」）

```
开工第一件事：  todoctl resume
手头看全：      todoctl bench
过程中随手记：  todoctl note R-0007 这次做到哪 发现了什么
声明计划下一步：todoctl update R-0007 --next R-0008 --next-step "先跑一遍 XX 用例"
收工最后一件事：todoctl note R-0007 收尾 --next-step "明天先跑一遍 XX 用例"
```

**只改状态、不留 `note` 的节点，三天后等于一个新节点** —— 你只看得到「还在推进」，看不到卡在哪一句话上。
`--next-step` 是收工时的最低成本投资：一句话，换下次开工少花十分钟重新进入上下文。

> 恢复锚点是秒级精度：与锚点同一秒内发生的改动不计入「自上次恢复以来的变动」。
> 真实使用间隔是分钟/小时级，无影响。

### 交错推进：绕行允许，但必须可见

真实工作不会按派生顺序走（做 1.1.2 → 被拉去做 2.1/2.2 → 才回头做 1.1.3）。
**绕行本身是正常决策，不阻断** —— 缺的从来不是纪律，而是**可见性**。

| 动作 | 命令 |
|---|---|
| 声明「这条线计划中的下一步是什么」 | `todoctl update <当前节点> --next <下一步节点>` |
| 随时看全手头有几件事、哪件最久没动 | `todoctl bench` |
| 回到那条线 | `todoctl resume <那条线的节点>` |

工具会在三处主动提醒你：`start` 别处时**当场打印绕行提示**、`check` 报 `W6`、`bench` 里标 `↷绕行中`。
**本来就打算绕，忽略即可**；怕的是绕了自己不知道。

⚠️ `--next`（节点指针）与 `--next-step`（文字）**不要混用**：前者可被校验，后者只给人看。

出现下列**任一**情况，**当场**执行 `add`，不要离开当前任务去做别的事：

| 触发场景 | 动作 |
|---|---|
| 做 A 时发现还缺一块能力 | `add --parent <A> --kind requirement` |
| 发现既有实现有缺陷 | `add --parent <当前> --kind bug` |
| 遇到岔路做了取舍 | `add --parent <当前> --kind decision`，`why` 写约束 |
| 被外部因素卡住 | `add --parent <当前> --kind blocker`，并 `block` 当前节点 |
| 用户临时插进来一个新要求 | `add --parent <最相关的祖先> --why "用户于 <时间> 提出"` |
| 讨论中推翻了旧方案 | 不要删旧节点 → `drop --reason "被 R-XXXX 取代"`，再 `add` 新的 |

### 什么时候**不**该建节点
- 一句话就能当场做完的琐事（不需要追溯、不需要收口）
- 已经收口的节点的等价重复（先 `search` 式地看 `TREE.md` 再决定）
- 纯执行细节（写什么变量名、用什么缩进）

判据：**「这件事三个月后有人问我为什么做、做到哪一步，我需要能回答吗？」** 需要 → 建节点。

## 三、收口纪律

```
done  = 我改完了           （实现层）
close = 已验证、已确认收口   （验收层，必须附证据）
```

`close` 的标准动作是四步，缺一步都不算完成：

1. **确认证据**：至少一条可复核的证据（commit / 测试 / 文件 / 人工确认）
2. **执行收口**：`close <id> --evidence "..."`
3. **回写祖先**（最常被漏掉）：本次收口是否使某个祖先的验收条件
   - **失效** → `update <祖先> --done-when "修正后的条件"`
   - **已达成** → 继续向上 `close`
4. **重跑视图**：`render`，确认折叠与告警符合预期

第 3 步防的是最典型的假收口：**叶子全关掉了，父需求其实没达成**。
`check` 能检测「closed 但仍有**未被显式接受**的未收口后代」（`E12`），也能拦「在已收口祖先下 `start`」——
但**检测不了**「后代全关、父目标仍未达成」。后者只能靠这一步人工确认。

> `--override-reason` 的作用域是**收口当时存在的那批后代**（记入 `close_override_ids`），
> 不是一张永久免检通行证：**收口之后**再冒出来的未收口子项一定会报 `E12`。
> 若真的还要继续做，正确动作是承认父项收早了、重新推进父项，而不是再 override 一次。

## 四、每周巡检（建议固定 10 分钟）

```
todoctl check                 # 1. 先清错误（错误会污染所有视图）
todoctl report --days 7       # 2. 看本周新增/完成/收口/阻塞
todoctl render                # 3. 已收口子树自动折叠
```

然后处理三类告警：

| 告警 | 含义 | 处置 |
|---|---|---|
| `W1` 深度 > 3 | 这条派生链**确实这么深** | **不改层级**。① 复核**每层派生是否如实**（有没有该拆未拆、或该并却硬拆）；② 阅读靠 TREE.md / 看板的「结构概览」按位置编号定位 |
| `W2` 同父未收口 > 7 | 这一层**确实平铺这么多** | **不插中间层**。① 可**归并语义重复**的子项（那是去重，让记录更如实）；② 其余照旧如实记录，阅读靠「结构概览」 |
| `W9` 父项**已放弃**但仍有未收口子节点（阈值 0，≥1 即报） | 活子挂在已终结的父项下，**归属未定**（`drop` **不做级联**；`--force` 只是允许父项独弃） | 逐个处理（推进 / `drop` / 收口），或**另立节点承载**并说明关系。子项处置完 W9 自然消失（不需要"接受"通道） |
| `W3` doing 但依赖未收口 | 在依赖没就绪时开工 | 退回 `blocked`，或明确记录并行推进的理由 |
| `W4` 超过 14 天未更新 | 停滞项 | 要么推进，要么 `block` 说明卡在哪，要么 `drop` |
| `W7` 祖先已收口/已放弃但仍在推进 | 有人在已关闭的父需求下继续开工（多为 `--force` 放行后遗留） | 二选一：把这项工作改建为自己的节点，或承认父项收早了、`update` 修正父项验收条件后重新推进 |

**不要用删除来让视图变干净**。删除会永久毁掉追溯链，而 `drop`（带理由）+ 折叠机制已经能解决视图清爽问题。

**也不要为了「视图好看」而改变层级**（含新建根）。父子关系是在**如实记录**需求之间的派生事实：
派生关系错了就改事实本身（`update` 修正、或另立节点把关系说清），**不能为了让树好看而凭空插一层、
或把一支挪到别处挂**。这也是本工具**刻意不提供改父（reparent）通道**的原因 —— 同族的另两条限制
（`--depends-on` 只能增不能删、`done_when`/`close_evidence` 收口后不可变）都由这条原则解释。

树太深 / 太宽不靠改造结构消解，靠**告诉你它在哪**：`check`、`resume`、各视图页眉都会打印一行
**结构概览**（最深（未收口）· 单层最宽 · 最大的一棵树，都带位置编号），`TREE.md` 与看板顶部另有完整区块。

> 唯一例外：当这一支**事实上就是另一个项目**时，另立新根是**如实记录**，不算整形。
> 判断依据是「它是不是另一套验收标准 / 另一个真源」，而**不是**「这样看起来更清爽」。

## 五、与其他记录的关系

这套系统是**唯一真源**，其余都是下游：

| 位置 | 关系 |
|---|---|
| `CHANGELOG.md` | 记录「改了什么」，本系统记录「为什么改、改到哪一步」。提交时两边都更新 |
| commit message | `refs` / `close_evidence` 里引用 commit hash，形成双向可追溯 |
| 项目 `MEMORY.md` | 只放跨会话必须生效的规则；需求明细留在本系统，不要抄进记忆 |
| 临时讨论 / 会话内笔记 | 讨论产生结论后，立刻把结论落成节点（`kind: decision`）+ 派生项 |

### 按线提交（别让 diff 成一锅粥）

一个 `tree.json` 里通常同时躺着几条需求的改动 —— 这是单文件真源的固有代价。
让提交仍然清楚的唯一办法是**按线组织叙述**：

```bat
REM 1) 先看这次都碰了哪些线
todoctl log --since "<上次提交时间>"

REM 2) 单独提交某条线时，抽出它自己的叙述
todoctl log --line R-0031 --since "<上次提交时间>" --commit-msg

REM 3) 提交（真源 + 日志 + 视图一起）
git add docs/requirements && git commit -m "..."
```

- **能拆就拆**：一次提交尽量只含一条线；拆不开时，commit message 按线分段写 —— `log --commit-msg` 正好给这个格式。
- **`journal.jsonl` 必须一起提交**：它是按线抽取叙述的唯一依据；丢了就再也无法回溯「哪条线什么时候改的」。
- **给它设 `merge=union`**：`.gitattributes` 里写一行

  ```
  docs/requirements/journal.jsonl merge=union
  ```

  追加式文件在两端各自追加时**必然冲突**，`union` 会保留双方新增行。合并后文件内顺序会交错 ——
  `log` 已按 `ts` 排序，所以读起来仍然是有序的（这也是这条策略成立的前提）。
- 视图（`TREE.md` / `ACTIVE.md` / `FOCUS.md` / `RESUME.md`）是派生物，提交便于 review，也可以在 `.gitignore` 里排除 —— 但**别两边各留一份手改的**。

### 封板纪律（`baseline`）

- **什么时候封**：一个可交付批次完成时（首版功能齐、上线前、拉评审前）。**不要天天封** —— 基线太密就退化成日志。
- **封板顺带是一次体检**：`baseline` 会拒绝在真源有错时执行（要求 `check` 通过）。
- **封板后不要回头改历史**：基线不可变。发现错就 `add` 一条修正并写明原因，或封一个新基线。

### 回滚纪律（`restore`）

- 回滚是**应急**，不是日常整理工具。要清理树用 `drop --reason` + 折叠机制。
- 回滚前先 `restore --list` 看清能退到哪；不加 `--yes` 时它只打印计划、**不动数据** —— 那是给你的确认机会，不是报错。
- ⚠️ 回滚会撤掉**其后的全部合法改动**，不只是你想撤的那一步。只想改一处，宁可 `update` 修正。
- 逐字段追溯用 `todoctl log`（含 before/after），**不要为了看历史去回滚**。

### 并发纪律（`tree.lock`）

- 单机单人正常使用**完全不需要关心**这把锁。
- 唯一禁忌：**不要在同一个真源上多开进程同时写**。第二个会被拒绝 —— 这不是故障，是保护。
- 多台机器上各有一份真源没问题（各自独立）；但**不要把两份真源混着用**，那会立刻产生分叉。
- 实现说明：锁持在 `<root>/tree.lock` 上，进程退出由系统自动释放；锁文件**常驻不删**
  （每次写入都删一个文件会往回收站灌记录）。

### 每次开工的第一条命令是 `resume`

它不是仪式：`resume` 会告诉你**上次做到哪、下一步、期间哪几条线动过、有哪些卡点**，
并把这些自动写进 `RESUME.md`。不跑它，等于每次从头重新进入上下文。

## 六、脱敏与公开镜像库

开发库的待办树通常含未完成需求、内部取舍与口语化措辞，**不要直接同步到公开版**。

```
todoctl export --out <公开版目录>
```

**`export` 恒脱敏，没有「不脱敏」模式。** 这是刻意的：本命令的全部意义就是产出可公开的副本，
给它加一个 `--full` 只会添一个**危险开关**（一旦被写进流水线就是不可逆泄露），
而「要一份完整副本」并不需要它 —— 真源目录本身就可读。

它会做三件事：

| 动作 | 说明 |
|---|---|
| 剔除 `internal` 节点**及其整条子树** | fail-safe：宁可多删不可漏。**不级联就会留下悬空 `parent`，导出的树是坏的** |
| `why` → `[已脱敏]`；清空 `notes` | 内部措辞与工作现场不进公开版 |
| 顺手清掉废弃字段 `refs` | 历史遗留，不再写入 |

**唯一无法自动脱敏的是 `title`** —— 所以每次导出都会打印「本次将导出 N 个节点，公开前请人工复核标题」；
没标任何 `internal` 时还会明确提示，避免"忘了标"变成静默泄露。

> **更省事的一条路**：公开版根本不需要待办树时，直接把 `docs/requirements/` 排除掉，压根不用 `export`。
> `export` 只服务于「要公开、但要公开一个子集」这一个场景。

在公开版仓库的同步流程中，把这个目录加入排除清单，或只提交 `export` 的产物。

## 七、反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 只手改视图文件 | 下次 `render` 覆盖，改动静默消失 | 改真源，重跑 `render` |
| 用位置编号引用节点 | 编号漂移后引用全错 | 只用 ID |
| 攒一批需求最后录入 | `why` 写不准，追溯链断 | 发现即 `add` |
| 用 `drop` 清视图 | 追溯链被主动销毁 | 折叠机制已足够 |
| 收口后不看祖先 | 假收口累积 | `close` 四步走 |
| 节点只填 `title` | 退化成 Excel | 至少补 `why` + `done_when` |
| 手工编辑 `tree.json` | 可能破坏成环/重复 ID | 走 CLI；若已手改，立刻 `check` |
| 把待办树推公开版 | 泄露内部信息 | `export`（恒脱敏）+ 人工复核标题；不需要公开就整目录排除 |
| 把 `internal` 当"反正导出会清 `why`" | 标题仍会泄露 | 只要这条线不能公开，就在树上标 `internal`（一处标注、整条子树剔除） |
| 手工编辑 `tree.json` 后再 `export` | 悬空 `parent` 会被带进公开版 | 只走 CLI；导出后对产物跑一次 `check` |
