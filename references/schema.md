# 数据模型与状态机

## 一、真源结构（`tree.json`）

```json
{
  "version": 1,
  "project": "my-project",
  "next_seq": 9,
  "focus": "R-0006",
  "last_resume": "2026-09-22 13:30:59",
  "resume_count": 4,
  "updated": "2026-09-22 12:45:07",
  "nodes": [ /* 扁平节点表，顺序即创建顺序 */ ]
}
```

`focus` / `last_resume` / `resume_count` 是**跨次交接**用的三个字段：
`focus` 指向当前推进的节点；`last_resume` 是恢复锚点（`RESUME.md` 用它与节点 `updated` 比较，得出「自上次恢复以来的变动」）；
`resume_count` 只是计数，便于判断这是第几次接手。

**为什么是扁平表而不是嵌套树**：父子关系只由 `parent` 指针表达，避免嵌套结构在编辑时被破坏；
树的形状永远可以从扁平表重建，反过来则不行。`next_seq` **只增不减**，保证 ID 不复用。

## 一之二、变更日志（`journal.jsonl`）

与 `tree.json` 并列的**第二个真源**，但它是**追加式**的：只增不改，永不重写。
每完成一次写入追加一行：

```json
{"ts": "2026-09-22 13:47:57", "op": "note", "id": "R-0028", "line": "R-0016", "detail": "顺手把角色分层表补完了"}
```

| 字段 | 说明 |
|---|---|
| `ts` | 秒级时间戳 |
| `op` | `add` / `start` / `block` / `unblock` / `done` / `close` / `drop` / `update` / `note` / `focus` / `resume` / `baseline` / `restore` |
| `id` | 被操作的节点（`baseline` / `restore` 这类全局操作为 `null`） |
| `line` | **归属线** = 该节点所属的最顶层根需求（全局操作为 `null`） |
| `detail` | 备注 / 阻塞理由 / 收口证据（截断至 200 字符） |
| `delta` | **字段级 before/after**：`{"R-0002": {"status": ["open","doing"]}}`；新增节点记为 `{"added": true}` |

`delta` 让 journal 从「发生了什么操作」升级为「状态怎么变的」——
这是 `log` 能显示 `open → doing`、以及回答「这个字段什么时候被改成什么」的依据。
它只记**短字段**（`status` / `blocked_by` / `next` / `next_step` / `parent` / `kind` / `title`），
长文本（`why` / `done_when` / `notes`）不进 delta，避免日志膨胀。

**为什么要单独存一份日志，而不是从 `tree.json` 反推：**

1. `tree.json` 只有「当前状态」。它记得住 `R-0002` 现在是 `closed`，但记不住「它是被谁、什么时候、以什么顺序推进的」。
2. **归属线是记录时的意图**，事后无法可靠还算（节点可能被移动、父节点可能被改）。
3. 提交时需要**按线抽取叙述**：`tree.json` 是一个文件，几条需求的改动必然混在一个 diff 里；
   `journal.jsonl` 提供了「哪些改动属于哪条线」这个索引，`log --line` 才能精确切分。

**约束**：只增不改、不手改、不进脱敏导出、随仓库一起提交。坏行会被 `log` 跳过，不阻断主流程。

## 一之三、基线（`baselines.json`）

第三个真源，同样是**只增不改**。每次 `baseline` 追加一条：

```json
{
  "id": "B-20260922-142754",
  "name": "v0.3 首版",
  "note": "首版功能齐了",
  "created": "2026-09-22 14:27:54",
  "prev": "B-20260922-101500",
  "stats": {"total": 45, "closed": 12, "unclosed": 33, "doing": 4, "blocked": 2, "max_depth": 4},
  "lines": [{"id": "R-0001", "title": "供货合同物资明细管理", "total": 20, "closed": 9,
             "unclosed": 11, "doing": 1, "blocked": 0, "dropped": 1, "progress": "9/19", "pct": 47}],
  "focus": "R-0029",
  "doing": [{"id": "R-0029", "path": "2.5", "title": "标签 × 权限交叉过滤"}],
  "journal_upto": "2026-09-22 14:27:54"
}
```

| 字段 | 说明 |
|---|---|
| `id` | **唯一**句柄，形如 `B-YYYYMMDD-HHMMSS`。同秒内连续封板会追加 `-02` / `-03`… —— 秒级精度会撞车，而它是「把所有成果合并成一个」的唯一可引用地址（撞车则 `--diff` 会静默取到错误的那条） |
| `prev` | 上一基线 ID —— `baseline --diff` 靠它串联 |
| `lines` | **按需求线聚合的进度**（`total` 已扣掉 `dropped` 作为分母） |
| `doing` | 封板时正在进行的项（回答「这个时点手头有什么」） |
| `journal_upto` | 该基线覆盖到 journal 的哪个时刻 |

`baseline` 会**拒绝在真源有错时封板**（基线必须是干净时点），并要求 `check` 通过。

`baselines.json` **解析失败时封板会被拒绝**（而不是按空处理再覆盖 —— 那会静默抹掉全部历史），
覆盖前还会把上一版另存到 `snapshots/baselines-last.json`。
旧数据里若存在重复 ID，`baseline --list` 会显式提示；`--diff <ID>` 取**最后一条**匹配项。

## 一之四、快照（`snapshots/`）

不是真源，是**写入前的自动留档**，用于回滚：

| 文件 | 内容 |
|---|---|
| `last.json` | 上一版（每次写入前覆盖） |
| `prev.json` | 上上版 |
| `tree-YYYYMMDD.json` | 当天首写前的状态，保留 30 天 |
| `baselines-last.json` | **上一版 `baselines.json`**（每次封板前覆盖）—— 基线文件损坏时的取回来源 |
| `pre-restore-<时间>.json` | 执行 `restore` 前另存的当前状态 —— 使**回滚本身也可逆** |

> `baselines.json` **不在**上面的 `last/prev` 滚动覆盖范围内（它有自己的 `baselines-last.json`），
> 因为它是独立真源、且被声明为「只增不改」。封板前会先解析校验：**解析失败直接拒绝封板**，
> 而不是按空处理再覆盖 —— 后者会静默抹掉全部历史基线。

回滚会自动**抬高 ID 水位**：扫 `journal.jsonl` 与 `baselines.json` 里出现过的最大 ID，
确保 `next_seq` 不小于它 —— **「ID 永不复用」不被回滚破坏**。

## 二、节点字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 不可变身份，`R-0001` 形式（`R-` + 至少 4 位序号）。**永不复用、永不重排** |
| `parent` | — | 派生来源节点 ID；根需求为 `null` |
| `kind` | ✅ | `requirement` 需求 / `task` 任务 / `bug` 缺陷 / `decision` 决策 / `blocker` 阻塞 |
| `title` | ✅ | 一句话标题 |
| `why` | ⭐ | **是什么触发了它**。写具体事实：在哪条需求、做什么动作时发现了什么 |
| `done_when` | ⭐ | **怎样才算收口**。进入 `doing` 前必须有，否则不能推进 |
| `status` | ✅ | 见下节状态机 |
| `created` / `updated` | ✅ | `YYYY-MM-DD` / `YYYY-MM-DD HH:MM:SS`（**秒级**：恢复锚点靠它做精确比较，全系统时间戳精度必须一致） |
| `closed_at` | closed 必填 | 收口日期 |
| `close_evidence` | closed 必填 | 证据数组，建议 `类型:值` 格式 |
| `close_override` | — | 带 override 收口时记录的理由（**只是理由，不再单独决定守卫是否生效**，见下一行） |
| `close_override_ids` | — | **收口时显式接受的那批未收口后代 ID**。`E12` 只对**不在该集合里**的未收口后代报错 —— 于是「收口后才冒出来的新子项」照旧被逮住。旧数据（只有 `close_override` 字符串）在首次 `load` 时懒迁移：把当前未收口后代视为已接受 |
| `blocked_by` | blocked 必填 | 阻塞原因（人/事/依赖） |
| `depends_on` | — | 跨分支依赖的节点 ID 数组 |
| `refs` | — | **已废弃，不再写入**。进行中的零散引用用 `notes`（免引号、带时间戳、追加式），收口证据用 `close_evidence`（强校验 + 视图展示）。旧数据里可能还留着空数组，`export` 时会顺手清掉 —— 该字段**没有任何消费者**，不再为新节点写入 |
| `notes` | — | 追加式进度记录：`<时间戳>  <文本>`，由 `note` / `done --note` / `close --override-reason` 写入。**这是跨次恢复的主要素材** |
| `next_step` | — | **下一步要做什么**（文字说明）。跨次恢复时直接展示；未记录时 `resume` 会明确提示补 |
| `next` | — | **计划中的下一步是哪个节点**（节点 ID）。可被 `check` 校验（E15/E16），也是检测「绕行」的前提：`doing` 且 `next` 指向的节点尚未开工 ⇒ `W6` |
| `internal` | — | 标记为内部节点：`export` 时**连同整条子树一并剔除**。用于「这条线不能公开」——`why`/`notes` 会被自动清空，但**标题**不会，所以只能整条剔除。忘记标记会在 `export` 输出里被点出来（「未标记任何 internal 节点」） |

`next_step`（文字）与 `next`（指针）**互不替代**，可以并存：

```json
{ "next": "R-0008", "next_step": "按 (tenant_id, tag_id) 重建联合索引再量一次" }
```

- `next` 让工具能回答「你是不是绕开了计划中的下一步」（`W6` + `bench` 的「↷绕行中」标记 + `start` 别处时的当场提示）
- `next_step` 让**人**能回答「回来之后第一件事干什么」

`next` 指向的节点若处于 `open` / `blocked`，即视为「尚未开工」——这是**绕行**（`W6`）的判据。
若它已经 `closed` / `dropped`，则原计划**已失效**（`W8`）—— 那不是绕行，而是计划本身不再成立，
`bench` 会标 `⌫计划已失效`，需要更新或清除 `--next`。

`why` 与 `done_when` 标注 ⭐ 是因为它们承担了这套系统的全部价值：
**`why` 支撑追溯（回答「这条为什么存在」），`done_when` 支撑收口（回答「能不能关」）。**
只填 `title` 的节点与写在 Excel 里没有区别。

## 三、状态机

```
                ┌──────────────┐
                │     open     │  未开始
                └──────┬───────┘
                       │ start（需 done_when + 祖先未收口）
                       ▼
   ┌───────────┐  unblock   ┌──────────┐
   │  blocked  │◀──────────▶│  doing   │  进行中
   └───────────┘   block    └────┬─────┘
                                 │ done
                                 ▼
                              ┌──────┐
                              │ done │  实现完成（⚠ 不等于收口）
                              └──┬───┘
                                 │ close（需证据）
                                 ▼
                             ┌────────┐
                             │ closed │  已验证收口
                             └────────┘

   任意非终态 ──drop（需 reason）──▶ dropped  已放弃
```

| 状态 | 语义 | 进入条件 |
|---|---|---|
| `open` | 已记录，未推进 | `add` |
| `doing` | 正在处理 | 有 `done_when`；依赖已收口；**祖先不得是 `closed`/`dropped`**（后两条可用 `--force` 放行） |
| `blocked` | 受阻停滞 | 必须给 `--reason` |
| `done` | 实现完成，待验证 | 从 `doing` |
| `closed` | 已验证收口 | 从 `done`；≥1 条证据；未被显式接受的未收口后代为 0（否则 `--override-reason`） |
| `dropped` | 主动放弃 | 必须给 `--reason` |

**为什么 `start` 要拦「祖先已收口」**：`E12` 拦的是**收口那一刻**状态不对，而这条拦的是**时间轴上更早的错位** ——
当你在一个已经 `closed` 的父需求下开工，父项的收口**从那一刻起就不再成立**，但树上看不出来。
默认拦；`--force` 可以放行，但会留下 `W7` 持续告警 —— **疏而有痕，比堵死更有效**。

**为什么把 `done` 和 `closed` 拆开**：绝大多数「假收口」都源于把「我改完了」直接当成「这件事结束了」。
拆开后，「实现完成」和「验证通过」成为两个必须分别跨过的门，前者不构成后者的证据。

**为什么放弃必须给理由**：`dropped` 是最容易被滥用的状态（用放弃来清空视图）。
强制理由可让放弃变成一个需要解释的决策，而不是一次静默删除。

## 四、ID 与位置编号

| | ID | 位置编号 |
|---|---|---|
| 例 | `R-0007` | `1.3.2` |
| 性质 | **身份** | **视图**（`render` 时按树形位置计算） |
| 可变性 | 永不变 | 会随插入/移动/删除整体变化 |
| 生成 | `next_seq` 只增不减，永不复用 | 每次 `render` 重新计算 |
| 用途 | 引用、依赖、证据、提交信息 | 人读时的「第几条的第几个子项」 |

位置编号的排序规则：同一父节点下按**创建顺序**排列（`tree.json` 中 `nodes` 的天然顺序）。
因此新增子节点总是追加在末尾，已有编号在正常情况下不会漂移 —— 但**引用仍然只能用 ID**。

## 五、派生关系的三种语义

同一个 `parent` 字段，在不同 `kind` 下含义略有差别：

| 派生场景 | 推荐 kind | `why` 怎么写 |
|---|---|---|
| 做需求时发现还缺一块能力 | `requirement` | 「推进 R-XXXX 时发现……，因此需要新增」 |
| 拆出来的具体施工步骤 | `task` | 「R-XXXX 的实现步骤之一」 |
| 过程中发现既有实现有缺陷 | `bug` | 「推进 R-XXXX 时发现 YY 场景下不成立」 |
| 遇到岔路做了取舍 | `decision` | 「在 A/B 之间选了 A，因为……（约束）」 |
| 被外部因素卡住 | `blocker` | 「等待 R-XXXX / 第三方接口就绪」 |

**`decision` 类型的价值常被低估**：几个月后「为什么当初这么设计」几乎不可能从代码里读出来，
而它是防止同一个取舍被反复推翻的唯一依据。
